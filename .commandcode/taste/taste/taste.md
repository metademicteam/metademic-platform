# Taste
- When the user asks to fix errors, they want ALL errors found and fixed comprehensively (e.g., running typecheck, lint, and tests to surface the full set and root causes), not just the immediately visible symptom — after fixing a reported error, the same bug pattern should be searched for and eliminated everywhere else in the codebase, then verified with typecheck/lint before declaring it done. Confidence: 0.75
- Wants demo/seed data to populate every role's view of the full platform workflow (e.g., submitted manuscripts must be assigned to the demo reviewer so their dashboard has content; accepted manuscripts should appear publicly) so each demo account has something meaningful to explore end-to-end. Confidence: 0.6
- Prefers receiving standalone, ready-to-run SQL scripts (self-contained and idempotent — `drop policy if exists` / `on conflict` / `create or replace` guards with usage notes embedded) that they can run themselves in the Supabase SQL Editor — e.g., seed scripts creating demo accounts for every role (author, reviewer, admin) with login credentials included in the file — so they can log in and explore the whole platform on their own. Confidence: 0.9
- Prefers to explore/test the platform hands-on themselves with demo accounts rather than having the agent test on their behalf; wants practical step-by-step login instructions (apply SQL files in order, start dev server, credentials table, what to look at per role, and gotchas). Confidence: 0.8
- Wants in-repo markdown documentation maintained alongside the code: a session-memory file (`memory.md` capturing stack, key commands, schema gotchas, known fixed issues) and a demo-users credentials file (`DEMO_USERS.md` with every role including admin) so future sessions and humans can pick up context quickly. Confidence: 0.7
- Cares about mobile responsiveness: UI screens (e.g., role dashboards) must be mobile-friendly, and sidebar/navigation must remain accessible on small screens (hamburger/drawer pattern), not desktop-only. When they report a UI issue they expect the fix to apply consistently to BOTH the desktop and mobile views of the same component (e.g., "fix it for both view" — a sidebar brand link made clickable on desktop AND in the mobile drawer). Confidence: 0.75
- When a previously-reported UI bug persists ("it doesn't work, fix it again"), expects a true root-cause fix verified against the real built output (e.g., inspecting the compiled CSS to catch conflicting Tailwind v4 theme rules, stale dev-server rebuilds/cache), not another surface patch layered on top of the failed one. Part of that is verifying the running dev server actually picked up the fix — a server process started before an edit can keep serving stale (server-only/service) code despite Next.js hot-reload, so restart the dev server and hard-refresh the browser to clear stale client chunks before declaring the fix done. The user runs their own dev server (e.g., on port 3000, started independently of any agent background task), so when a fix appears ineffective the agent should check which PID is actually listening on the port and instruct the user to restart their own server rather than assuming the agent's process serves them. Confidence: 0.9
- Wants dropdown/popover menus to have explicitly-set solid backgrounds (e.g., `bg-white`) rather than relying solely on theme variables that can silently resolve to an invalid value and render transparent — treat the theme-indirect color mapping as fragile and add a defensive explicit style when it's the visible symptom. Confidence: 0.6
- Prefers a light-only UI: dark mode / theme switching was removed outright ("remove dark mode feature it messed up the whole UI") and the expectation is that all dark-mode infrastructure is stripped completely (provider, toggle, `prefers-color-scheme` CSS block, every `dark:` variant), with the platform staying light-only by design rather than keeping the toggle. Confidence: 0.85

Confidence: 0.8
- When the user names a specific skill (e.g., "impeccable skill"), activate it and follow its full workflow rather than approximating: load project context, respect the skill's quality bar/craft floor, run its mechanical detector on changed targets, and verify with typecheck/lint before summarizing. - Reports bugs as terse one-line symptom reports that name the exact route/file (e.g., "/author/submissions/new cloudinary upload is not showing") or paste a raw error response body (e.g., a full 500 JSON payload) followed by "fix it", often attaching screenshots of the dev-server terminal log (repeated 500s) alongside the visible UI symptom (e.g., "no pdf upload option showing" was actually a stuck upload step because every POST /api/manuscripts 500'd, blocking draft creation). - Dead/placeholder UI affordances (e.g., an `<a href="#" onClick={(e) => e.preventDefault()}>Download</a>` stub in a server component) should be made genuinely functional when fixed — wire them to real data (e.g., select `secure_url` from the DB and render a real download anchor) rather than merely silencing the error or removing the element. Confidence: 0.5
- For silent background failures (e.g., a wizard autosave that swallows a 500 and leaves the UI stuck on a generic "Saving draft…" state with no visible error), prefers errors to be surfaced in the UI — a visible red banner showing the actual server error message — rather than only console-logged, so the true failure is diagnosable at a glance; background fetches should throw on `!res.ok` instead of silently continuing. Confidence: 0.55
- For Supabase/Postgres RPC failures, expects fixes to follow the repo's established DB convention: recreate the function as `SECURITY DEFINER SET search_path = public`, `GRANT EXECUTE` to `authenticated`/`service_role` (anon where harmless), deliver as a self-contained idempotent migration file (`create or replace` / `if not exists`), AND patch `schema.sql` (the source of truth) to match so a fresh DB build gets the same fix — the live DB only changes when the user runs the migration. Because the live DB can lag the migrations (no supabase CLI on this machine, so the user applies SQL manually in the SQL Editor), also expects the app layer to be made resilient so failures never 500 even before the migration is applied — e.g., `createManuscript` tries the RPC and falls back to generating the identifier client-side/service-side if the RPC errors or returns null. Confidence: 0.75
- Prefers defensive app-layer fallbacks over relying on DB state: writes that can be blocked by RLS (e.g., manuscript/version INSERTs) should retry with the service-role admin client (which bypasses RLS) when the anon-key call errors, and the fallback should be bulletproof rather than narrowly conditional — retry on ANY error (not just messages matching an RLS regex), and surface the admin client's actual error if the fallback also fails instead of silently swallowing it. Confidence: 0.6
- When the user pastes dev-tooling noise (e.g., a React hydration-mismatch warning caused by the Grammarly browser extension injecting `data-gr-ext-installed` attributes onto `<body>`), they want it silenced cleanly in the code — here by adding `suppressHydrationWarning` to the `<body>` element (matching the existing one on `<html>`) rather than ignoring it, but also wants the cause (browser extension, not an app bug) clearly identified in the explanation. Confidence: 0.5
